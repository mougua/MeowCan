# MeowCan 游玩卡顿排查与优化方案（Codex）

> 作者：Codex
> 日期：2026 年 9 月 28 日
> 状态：已修复视觉时钟并完成模拟器前后对照；真机尚未验证
> 范围：桌面端与平板横屏的游玩阶段

## 结论与责任边界

当前证据不能证明卡顿由 PixiJS 单独造成。MeowCan 已统一到 Pixi Ticker，预上传了主要纹理，并复用多数音符精灵。最值得验证的剩余风险是：视觉时钟推进不均匀、密集谱面使对象池在游玩中扩容、音频定时调度一次处理过多事件，以及特定浏览器后端的呈现抖动。

本方案以**减少可感知的停顿**为目标，而非提高平均 FPS。实施者必须保存修复前后的录制与指标。只有同机、同浏览器、同谱面复测达到下文验收标准，才能宣称修复有效。本文已记录模拟器上的修复前后对照，证明该环境中视觉时间推进更均匀。其他设备与卡顿成因尚未验证。

## 当前代码核对

1. `web/src/game/renderer.ts` 的 `init()` 已设置 `antialias: false`、DPR 上限 1.5，并使用 Pixi Ticker。它还调用 `renderer.prepare.upload()`。旧文档 `rendering-perf-audit.md` 中“双 rAF”“未预热纹理”“长音符每帧重画 Graphics”等描述已过时。
2. `prewarmNoteSprites()` 预建 64 个音符头、32 个长音符主体和 32 个尾部精灵。`renderFrame()` 在池不足时仍会调用 `new Sprite()`。能否触发取决于实际谱面密度。
3. `renderFrame()` 用增量候选列表维护临近音符，已不再从谱面开头逐帧扫描。当前无需照旧审计重新实现游标。
4. `web/src/audio/synth.ts` 每 30 ms 调用一次 `scheduleBgm()`，预读 120 ms。两个事件循环都会处理窗口内全部待调度事件。需要测量单次耗时和事件数量。
5. `?fps` 每秒更新一次平均值。一次 40 ms 停顿可能被其余正常帧掩盖。
6. `web/src/game/visual-clock.ts` 每帧把视觉时间限制在音频时间前后 4 ms。AGY 的[并行分析](pixijs-stutter-plan-agy.md)指出，这可能造成“FPS 正常，音符位移却不均匀”。这是值得优先验证的假设。Web Audio 的常见渲染量子是 128 帧，在 48 kHz 下约为 2.7 ms，不能直接假定音频时间必然以 10 ms～20 ms 阶梯更新。[MDN 的 `currentTime` 说明](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/currentTime)也指出，相邻读取可能相同。对现有 `VisualClock` 模拟 60／120／144 Hz 帧与 128／48,000 秒音频步长，1,000 帧内没有触发 4 ms 钳位；模拟 512／48,000 秒步长时则频繁触发。模拟结果不能代替目标设备实测。

## 安卓模拟器上的首轮实测

2026 年 9 月 28 日，在本机安卓模拟器中运行 MeowCan 自动演奏，使用遨游浏览器 7.2.3.320（Android WebView 110.0.5481.154.1）、Android 12、WebGL、48 kHz 音频和 60 Hz 显示。页面来自 `http://172.16.25.152:3000/`。通过 WebView 调试接口，连续采集了约 15 秒、900 帧的 `requestAnimationFrame`、`AudioContext.currentTime` 与 `VisualClock` 值。采样在每帧的独立回调中进行，没有修改游戏源码。

| 指标 | 观察值 |
| :--- | :--- |
| 动画回调帧间隔 | p99 约 16.667 ms；900 帧中 1 帧约 33.333 ms |
| 每帧读到的音频时间增量 | 主要为 0、约 10.667、21.333、32 和 42.667 ms |
| 视觉时间增量 | 77 帧小于 8 ms；42 帧大于 25 ms |
| 视觉与音频时间的绝对差 | 901 次采样中，574 次约为 4 ms |
| 音符对象池长度 | 头部 64、身体 32、尾部 32，采样结束时未见扩容 |

这组数据支持“模拟器中的音符位移不均匀与视觉时钟钳位有关”。动画回调大多准时到达，视觉时间却出现慢进与快进。逐帧读取到的 10.667 ms 倍数只是**主线程观察到的增量**；它不能证明 Web Audio 内部渲染量子变成了 512 采样点，也不能推广到真机或其他浏览器。当前采集未包含 Chrome 火焰图、GPU 呈现时间及玩家主观标记的卡顿瞬间，因此尚不能断定它解释了全部卡顿。屏幕录制本身会影响帧时间，正式验收应在关闭录制后重新采样。

### 修复后的同机对照

在 `web/src/game/visual-clock.ts` 中移除了每帧的 ±4 ms 硬钳位。视觉时间继续按帧间隔推进，并通过原有的指数平滑校正音频误差。音频时间发生明显跳变或渲染长时间暂停时，时钟仍会重新同步。修改后，在同一浏览器、同一首曲目、同一速度档位进行两次约 15 秒自动演奏采样；这两次采样均没有开启屏幕录制。

| 指标 | 修改前 | 修改后第 1 次 | 修改后第 2 次 |
| :--- | :--- | :--- | :--- |
| 样本帧数 | 900 | 898 | 900 |
| 视觉时间增量小于 8 ms | 77 帧 | 0 帧 | 0 帧 |
| 视觉时间增量大于 25 ms | 42 帧 | 1 帧 | 0 帧 |
| 视觉时间增量 p99 | 约 34.7 ms | 约 18.7 ms | 约 17.9 ms |
| 视觉与音频时间差 p99 | 约 17.3 ms | 约 16.2 ms | 约 13.8 ms |
| 动画回调间隔 p99 | 约 16.667 ms | 约 16.667 ms | 约 16.667 ms |

第 1 次修复后采样有 1 帧约 33 ms 的动画回调间隔，视觉时间也出现一次较大的推进；第 2 次采样没有该现象。短时对照说明视觉时间的周期性停滞／追赶在此模拟器上显著减少，但不能保证没有其他来源的偶发掉帧。判定和按键音效继续使用音频时间，未更改其代码。修复后的视觉与音频时间差 p99 小于 17 ms，仍需在真机和人工击键下检查手感。

后续把视觉时钟的帧时间改为 Pixi Ticker 当前帧的 `requestAnimationFrame` 时间戳，避免回调执行时刻的微小波动。在同一模拟器的 Ice Cap、速度 12 对照中，音符单帧位移 p99 从约 8.85 像素降至约 8.46 像素；用户反馈为“略有改善”。60 Hz 下该速度仍约每帧移动 8 像素，不能把固定刷新率的阶梯感等同于程序掉帧。

对 Ice Cap 的 48～109 秒中段做了分段采样。同屏音符头最多 13 个，候选音符最多 14 个，预建池容量为 64；没有观察到池扩容。动画回调绝大多数为 16.667 ms，仅在其中一段记录到 2 帧约 33 ms。模拟器的 SurfaceFlinger 近期呈现间隔也保持约 16.667 ms。用户仍报告中段可感知的顿挫，因此这些客观指标尚不能解释全部主观感受；不应在缺乏证据时扩充对象池或宣称问题完全解决。

## 先建立可复现基线

在目标设备上固定浏览器版本、显示器刷新率、窗口大小、缩放比例、渲染后端、音源、曲目和难度。选一首容易复现卡顿的谱面，再选一首低密度谱面作对照。使用正式构建运行，避免开发服务器和 DevTools 常驻造成额外干扰。

每种条件完整播放 3 次。保存 Chrome Performance 录制，并记下卡顿发生的歌曲时间。至少做四组对照：WebGPU／WebGL × 过程音源／音色库。若设备不支持某组，记录实际后端与缺失原因。用 [Chrome Performance 面板](https://developer.chrome.com/docs/devtools/performance)查看 Frames、Main 线程、GPU 轨道及长任务；出现卡顿时分析前后约 2 秒的录制。

增加仅在诊断开关下启用的轻量记录：连续帧间隔、音频时间增量、视觉时间增量、4 ms 钳位触发次数、`renderFrame()` 耗时、`scheduleBgm()` 耗时和事件数、三类对象池长度与扩容次数、`performance.memory`（若可用）、实际 `app.renderer.name`。采样数据保留在内存环形缓冲区，结束后一次导出。游玩中逐帧打印控制台会污染测量。音频另记可听见的断续，以及 `AudioContext` 是否暂停。

以显示器帧周期 `T = 1000 / 刷新率` 为基准。记录 p50、p95、p99 帧间隔，以及超过 `2T` 的帧数／分钟。60 Hz 的 `2T` 约为 33.3 ms，120 Hz 约为 16.7 ms。这是项目的诊断阈值，不是 PixiJS 保证值。若 FPS 数字稳定而人眼仍见顿挫，应查看 Chrome 的 dropped／partially presented frame；单靠 JavaScript 的帧间隔无法覆盖全部呈现问题。[开发者案例](https://github.com/pixijs/pixijs/issues/10247)也提示了这一点。

## 按证据实施

### 优先验证：视觉时钟的推进是否跳变

模拟器实测已确认 4 ms 钳位反复触发，因此已改为平滑校正。后续应继续比较相邻帧的视觉时间增量与墙钟增量，并验证长帧、暂停、切后台与 seek 后的重新同步。尤其要观察视觉时间相对判定音频时间的偏差。若其他设备没有相同现象，不能把这项修复当成该设备所有卡顿的解释。

### 第一优先级：消除游玩中对象池扩容

若卡顿帧附近的对象池长度增加，播放前按谱面估算同屏峰值，预建音符头、长音符主体和尾部。估算必须使用谱面原始 tick、`tempoMap`、当前速度档位与现有可见窗口逻辑。速度可能在游玩中变化，预建量应覆盖允许的速度范围或在切换速度时先完成扩容。对异常谱面设内存上限，并记录未覆盖的峰值。游玩热路径保留兜底创建，但正常谱面验收要求扩容次数为 0。不要直接把固定池容量设成一个很大的常数。

只在准备阶段建池，避免把卡顿移到倒计时。播放后检查画面层级、长音符接缝、切歌后池复用和内存占用。

### 第二优先级：拆分音频调度尖峰

若 `scheduleBgm()` 的耗时与卡顿帧重合，先找出高峰事件数量和耗时来源。重点区分过程音源、音色库的 `scheduleMidiMessage()`，以及首次音色初始化。对可提前准备的音色和数据移到开局前；对确实需要批量排程的事件，调整调度窗口与频率后成对复测。

不得仅按固定事件数截断当前窗口，否则可能漏播或迟播。任何分批方案都要保证每个事件在其音频时间前进入 Web Audio，并验证按键音效延迟、伴奏同步与暂停／恢复行为。120 ms／30 ms 的现值先作为基线保留。

### 第三优先级：针对实际 GPU 或呈现问题

若主线程耗时正常，但 Chrome 标出掉帧或 WebGPU 与 WebGL 差异明显，先固定更稳定的后端做对照，再看 GPU 时间、分辨率和显存。若首次出现某皮肤或特效才停顿，检查其纹理是否已进入 `prepare.upload()`。仅在证据指向 draw call 时考虑图集或静态层缓存。缓存会增加纹理内存，频繁变化的层不适合直接缓存。

不要把关闭 PixiJS 纹理 GC、降低 DPR、限制 60 FPS 或大规模重构渲染器作为首个修复。这些措施可能掩盖问题或增加输入反馈延迟，必须分别做 A/B 复测。

## 验收与回退

在相同设备和谱面上，优化版需同时满足：

1. 三次完整播放中，用户标记的卡顿区间不再复现；超过 `2T` 的帧数／分钟较基线下降至少 50%，且 p99 帧间隔不恶化。若基线本就少于每分钟 2 帧超阈值，以完整播放无新增超阈值帧和录制无对应掉帧为准。
2. 音频无新增断续、丢音或节拍漂移；按键判定与按键音效没有可测的延迟退化。
3. 普通游玩期间对象池扩容次数为 0；若优化对象是音频或 GPU，此项仅作监控，不作为其修复的因果证明。
4. 桌面端与平板横屏各复测至少一种目标设备；两种渲染后端只需验证设备实际支持的组合。

若优化后尖峰数量上升、音频质量下降或内存持续增长，回退该项并保存前后录制。验收数据应附设备、浏览器、后端、曲目、音源、刷新率和提交号，使结论可复核。未拿到对照数据时，状态保持“待验证”。
